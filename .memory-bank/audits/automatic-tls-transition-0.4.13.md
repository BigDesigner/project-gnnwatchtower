# Automatic TLS transition exposure assessment

Before: all application APIs shared an existing HTTP port in legacy installations; 0.4.12 switched to TLS with an incomplete manual trust migration. After: same port accepts TLS and a strictly limited plaintext GET for the pre-existing public signer-key route. Plaintext credential/telemetry APIs are rejected. No additional port, management protocol, system trust store or privilege is introduced. A nonce-bound Ed25519 signature authenticates the public TLS certificate using the agent's existing signer pin. Missing pins cannot be bootstrapped over unauthenticated HTTP. Installer trust is delivered through the authenticated operator HTTPS session and kept only in the application directory. This narrows existing plaintext exposure; the public signed trust metadata contains no secrets. Protocol classification is bounded to 64 workers and a three-second read deadline.

Only an already TLS-enabled fleet is offered automatic signed remote updates before cutover. Legacy HTTP installations cannot prove remote signer custody; those agents require the authenticated panel installer, with the local appliance agent updated through the existing root-operated updater. Agents offline during that window or lacking a pre-existing trustworthy signer pin require the same panel-generated installer when reachable; no silent insecure fallback is permitted.

## Delivery and validation limits

The frontend now obtains both installer scripts through the authenticated API instead of constructing bare binary-download commands. Both installers embed public certificate trust and the existing signer public key, check the downloaded binary hash, and do not modify the operating system trust store. Windows uses a per-request exact certificate pin with hostname/time checks; Linux uses curl's dedicated CA file. No certificate-verification bypass is introduced.

Update builds happen before the current service is stopped. The updater snapshots the stopped data directory, preserves certificate and signing identity, prepares missing settings, checks HTTPS using local certificate trust, and attempts server rollback on failure. It does not claim distributed agent rollback. Legacy HTTP agents with unverifiable remote pin custody require the authenticated installer; only a previously TLS-enabled fleet is automatically offered signed remote upgrades. The local appliance agent receives its trust file directly from the authorized local updater.

Vite production compilation, Linux amd64 server/agent compilation, Windows amd64 agent compilation and shell syntax checks completed. Functional tests, PowerShell execution, apt/systemd/container execution and live customer deployment were not performed. A browser's first trust decision for a private certificate still requires fingerprint verification against the server console; this cannot be safely inferred from the same unauthenticated network connection.
